================================================================================
RELATIONSHIPS SUMMARY
================================================================================

1. users (1) → (N) sessions
   - One user can have multiple active sessions
   - CASCADE DELETE: Delete sessions when user is deleted

2. users (1) → (N) generation_history
   - One user can have multiple generation attempts
   - CASCADE DELETE: Delete history when user is deleted

3. generation_history (1) → (N) sprites
   - One generation can produce multiple sprites (e.g., animation frames)
   - NULL on delete: Sprites remain if generation history is deleted

4. generation_history (1) → (N) music_tracks
   - One generation can produce multiple tracks (e.g., variations)
   - NULL on delete: Tracks remain if generation history is deleted

5. generation_history (1) → (N) sound_effects
   - One generation can produce multiple SFX
   - NULL on delete: SFX remain if generation history is deleted

6. generation_history (1) → (N) scripts
   - One generation can produce multiple scripts
   - NULL on delete: Scripts remain if generation history is deleted

7. users (1) → (N) audit_logs
   - One user generates many audit log entries
   - SET NULL: Preserve audit logs even if user is deleted

8. users (1) → (N) sprites
   - One user owns many sprites
   - CASCADE DELETE: Delete sprites when user is deleted

9. users (1) → (N) music_tracks
   - One user owns many music tracks
   - CASCADE DELETE: Delete tracks when user is deleted

10. users (1) → (N) sound_effects
    - One user owns many sound effects
    - CASCADE DELETE: Delete SFX when user is deleted

11. users (1) → (N) scripts
    - One user owns many scripts
    - CASCADE DELETE: Delete scripts when user is deleted

================================================================================
INDEX STRATEGY
================================================================================

Primary Indexes (Automatic):
- All primary keys (id, sprite_id, track_id, etc.)
- All unique constraints (username, email, token)

Secondary Indexes (Performance):
- users.username          → Fast user lookup
- users.email             → Fast email lookup
- sessions.user_id + is_active → Fast active session lookup
- sessions.expires_at     → Fast session cleanup
- sprites.user_id + created_at → Fast user asset listing
- sprites.category        → Fast category filtering
- music_tracks.user_id + created_at → Fast user asset listing
- music_tracks.category   → Fast category filtering
- sound_effects.user_id + created_at → Fast user asset listing
- sound_effects.category  → Fast category filtering
- scripts.user_id + created_at → Fast user asset listing
- scripts.script_type     → Fast type filtering
- generation_history.user_id + created_at → Fast history lookup
- generation_history.status → Fast status filtering
- generation_history.asset_type → Fast type filtering
- audit_logs.user_id + timestamp → Fast user audit trail
- audit_logs.action       → Fast action filtering
- audit_logs.resource_type + resource_id → Fast resource audit

================================================================================
DATA TYPES & CONSTRAINTS
================================================================================

String Sizes:
- UUID/ID fields: 36 characters (standard UUID)
- Short strings (username, email): 255 characters
- URLs/paths: 512 characters
- Text fields: Unlimited (description, prompts, events)

JSON Fields (PostgreSQL JSONB):
- metadata: Flexible key-value storage
- input_parameters: Generation parameters
- output_metadata: Generation results
- events: GB Studio event structure
- tags: Array of tag strings
- details: Audit log details

Enums:
- UserRole: admin, user, guest
- AssetType: sprite, music, sfx, script
- GenerationStatus: pending, in_progress, completed, failed, cancelled

Timestamps:
- created_at: Set on creation (NOT NULL)
- updated_at: Set on creation and update (NOT NULL)
- completed_at: Set when generation completes (NULLABLE)
- expires_at: Set for session expiration (NOT NULL)
- last_login_at: Updated on successful login (NULLABLE)

================================================================================
REDIS CACHE SCHEMA
================================================================================

Key Patterns:
┌────────────────────────────────────────────────────────────────────────────┐
│ session:{session_id}        → User session data (24h TTL)                  │
│ cache:llm:{hash}            → LLM response cache (5m TTL)                  │
│ cache:kb:{hash}             → Knowledge base query cache (15m TTL)         │
│ cache:asset:{asset_id}      → Asset metadata cache (1h TTL)                │
│ ratelimit:user:{user_id}    → Rate limiting counter (window-based)         │
│ ratelimit:ip:{ip_address}   → IP-based rate limiting                       │
└────────────────────────────────────────────────────────────────────────────┘

Data Types:
- String: Simple key-value (sessions, cache)
- Integer: Counters (rate limiting)
- Hash: Complex objects (user preferences)
- Set: Collections (active users)
- Sorted Set: Leaderboards, time-based data

TTL Strategy:
- Short-lived (5m): LLM responses, temporary data
- Medium-lived (15m-1h): Knowledge base, asset metadata
- Long-lived (24h): User sessions
- Permanent: Configuration, feature flags
